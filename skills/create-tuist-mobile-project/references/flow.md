# Create Tuist Mobile Project Flow

1. **Capability detection** – Check `git`, `gh`, `gh auth status`, `mise`, `mise exec -- tuist version`, and `mise exec -- tuist auth whoami`. Each capability is either available, installed but not authenticated, or missing. The summary drives the next section, but it must not hide any of the supported modes.
2. **Question format** – Use one question per turn. For branch decisions, present short labeled choices such as `A`, `B`, `C`, then wait for a single answer. Never ask for two fields in one reply and never ask for comma-separated values.
3. **Mode selection** – Ask the user to choose between `local-only`, `github-backed`, and `github-and-tuist-cloud`. If a capability is missing, surface the block and ask whether to postpone the mode or fix the tooling. The skill never downgrades silently and never filters out blocked modes.
4. **Template selection** – Ask whether to scaffold the pure iOS template or the iOS + Catalyst template. Keep template aliases stable so the CLI payload becomes deterministic.
5. **Metadata collection** – Ask questions in this order, one field at a time: project name; destination path; GitHub owner only when the selected mode is `github-backed` or `github-and-tuist-cloud`; repo name, where any default derived from the project name must still be explicitly confirmed by the user; repo visibility only in those GitHub-backed modes; bundle identifier; default iOS simulator device; then, when the selected mode is `github-and-tuist-cloud` and the current capability state supports it, ask separately whether to create the Tuist Cloud project and whether to run `tuist setup cache`; finally ask about initial commit and push choices.
6. **Optional overrides** – `full_handle` is derived from the confirmed owner and repo name by default. Only surface it as an override when the user needs to bind to a specific existing handle or correct the derived value. `cache_service_slug` is derived from that handle by default and belongs in the JSON handoff, not in the default Task 1 interview.
7. **Fail-closed directory branch** – Before local scaffolding, if the target directory already exists, stop and ask the user to choose `reuse`, `replace`, or `abort`.
8. **Fail-closed repo-name branch** – Before GitHub repo creation, if the requested repo name is already taken, stop and ask whether the user wants to choose another repo name. If they decline, force an explicit choice to switch modes or abort.
9. **Fail-closed full_handle branch** – Before Tuist Cloud creation, if the requested `full_handle` already exists, stop and ask whether the user wants to bind to that handle or choose another handle.
10. **Confirmation checkpoint** – Explicitly confirm GitHub repo creation with the chosen visibility, Tuist Cloud project creation, `tuist setup cache`, initial commit creation, and push. No action executes without a yes/no answer, and `not_asked` approvals must be resolved before later tasks attempt side effects.
11. **GitHub execution** – If confirmed and the chosen mode is `github-backed` or `github-and-tuist-cloud`, the orchestration layer should run `gh repo create` with the requested visibility. Do not treat this as permission to push later steps automatically.
12. **Local scaffolding** – Resolve the destination directory, prepare a local template source path, ensure any existing target directory is handled only through the explicit `reuse`, `replace`, or `abort` branch, and in later tasks invoke `bin/zach-mobile-init --config <path-to-json-config>` from the Zach-Skills repo root. The future CLI consumes the prepared local template source and performs local placeholder mutation only.
13. **Cloud and cache** – When Tuist Cloud creation is separately confirmed, the orchestration layer should run `mise exec -- tuist project create <full_handle>` from the chosen project root. When cache setup is separately confirmed, it should run `mise exec -- tuist setup cache --path <destination_path>` afterward.
14. **Warm and verify** – Treat `mise run warm-external-cache` as the default local post-init setup/verification step. Run it from the generated `destination_path`, not from the Zach-Skills repo root.
15. **Commit** – If the user confirmed initial VCS setup, the orchestration layer should run `git add` and `git commit` only after the warm/generate flow completes.
16. **Push and final output** – Push only if the user explicitly confirmed push. Then present the resulting project path, repo URL when applicable, and the ready-to-use commands for run/build/test/share recorded in the template flows.

`scripts/create_mobile_project.py` is the current helper surface for capability detection, blocker reporting, strongly typed approvals, approval gating, and in-memory payload assembly. The CLI already exists; later tasks will add the final interview wiring plus payload serialization around it.
